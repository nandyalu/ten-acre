## The auto trader: what it is now

**This section is the current contract — what the agent is shown, what it may ask for, and what Python refuses.** For how it got that way, and why any given rule exists, see the changelog in [JOURNEY.md](../../JOURNEY.md). **For whether the model actually reads any of it, see `agent-probes.md`**, which holds every probe result and its verdict. A bullet below states the verdict in one clause; the samples and the quotations are there.

**Record every behaviour change there before making it** — a reworded rule, a new number in the prompt, a different limit. Behaviour is mostly prompt, so an experiment that runs for a month across three prompt revisions has three experiments in it, and no way to tell them apart afterwards unless someone wrote down when the question changed.

### What the agent is shown

One prompt per decision pass, assembled by `agent.build_prompt()`.

**Since 2026-09-21 the order is a declared list at the end of `build_prompt`, and every section carries a `##` heading and a `---` rule above it.** The sections are gathered into four groups, each named once by a `#` heading above its first non-empty section: **Since you last looked** (what changed in the app, what the rules noticed, what its own last answer did), **What is true now** (the regime, the account, the holdings, the tables, its record), **Now** (the clock, why the pass is happening, the agent's standing notes) and **What you can do** (research, the rules, the next wakeup, how to answer). Each section is built by its own function that knows nothing about its neighbours; `_joined` drops the empty ones, adds the heading and puts one rule between the rest. A section that needs to move is one entry moved in that list. **Do not reorder it without a probe** — placement here is measured, not guessed (`agent-probes.md`).

**"Now" was the first group until later the same day, and moving it is the riskiest change made to this prompt.** It was first because everything below it is read against it. It is third because the agent is deciding about a book rather than about a time, and a note it wrote to itself reads better against an account, a holding and a signals table already in hand. Asked what order it wanted, 9 of 14 samples put the book first — and 3 of the same 14 said they carried the market being closed down the prompt, which argues the other way. **Judge this on whether the clock is still read from its new place, not on the preference.**

The table is the order. The numbered notes under it are keyed to sections, not to positions, and the numbers are stable references that other parts of this file point at; **they are not the order and never were**. Until 2026-09-21 this section claimed they were, and it had been wrong about eight of them since the watchdog and outcome blocks moved above the tables on 2026-09-12.

**A heading is load-bearing where a wake reason points at it, and so is the direction word beside it.** `describe_wakeup` names "What was noticed since your last pass", and `_asked_again` names "What your last answer did". Rename either and the pointer points at nothing, which is the exact failure the "no wake reason may promise a section" rule was written for. **Both pointers say "above" since 2026-09-21**, because the "Now" group moved below "What is true now" and every section they name is now higher up the prompt; a pointer with the right heading and the wrong direction fails the same way. **It named four headings earlier the same day**, one per section; those four are one section now and the pointer is one sentence.

The notes:

1. **The clock** — the Eastern time, the date, and how long until the close. **It was the first section from the beginning until 2026-09-21**, because everything below it is read against it and because the agent chooses its own next wakeup, which is a question about the time. It now sits below "What is true now" and above the rules, on the hypothesis that the agent is deciding about a book rather than about a time. **What must stay true either way: the clock is above the rules and the answer**, because the closed-market rule and the wakeup it chooses both depend on it. A test pins that.
1b. **Why it is awake, and the note the last pass left for this one.** Several things start a pass — its own chosen time, something noticed while it slept, the last call before the close, a stop or target filling, a position left unguarded — and it was told none of them until 2026-09-12; the labels were log lines. **A change to the app was one of them until 2026-09-21**, when that mechanism was removed. `next_wakeup_note` is the other half: the agent has no memory between passes, and the prompt carries prices and positions but never conclusions, so this is the one place it can hand something to its own future self. **No wake reason may promise a section** — one said "see what it was, below" and the earnings path reaches the same pass with no alerts, so the prompt pointed at nothing and seven probe runs read straight past it. `build_prompt` adds the pointer, because only it knows whether the section is there.

   **The ask and the reason are at opposite ends of the prompt since 2026-09-21, deliberately.** Why the pass is happening stays under the clock, because it is read against everything below it. The ask to choose a wakeup — and the computed instant the agent gets if it names none — is `describe_next_wakeup`, between the rules and the answer shape, beside the field it fills. Colocating those two removed a third statement of one fact: the ask used to end "If you give no time, you are asked at the following open", which is now the line directly above it. **Probed the same day: the fallback instant is still read from the bottom (7 of 7 chose it), and 7 of 7 named a wakeup and wrote a note.**

   **An early wake says that it is early, and asks again (2026-09-13).** A sharp move, the earnings check, a stop filling and a position left unguarded all fire the pending alarm early (a restart with new change notes did too, until that mechanism was removed on 2026-09-21) through `scheduler.wake_agent_now(label)`, and until that date the alarm always said "You asked to be woken now". The label now travels with the alarm in `_early_wake_label`. When the planned wakeup is still ahead, `describe_wakeup` shows the note beside the time it was written for, and asks for `next_wakeup` and `next_wakeup_note` again, because the early pass replaces the planned alarm. **Read, 4 of 4, and the ask is what does the work rather than the reason line** (`agent-probes.md`). **A later turn of the same pass names the wake as history** — "Why this pass started" — and adds "Why you are asked again", built in `build_prompt` from whichever of the outcomes, the readings and the refusals are really in that prompt.

   **Two more early wakes, added 2026-09-16, close a gap where a real event had no witness but Discord.** A resting stop or target firing on its own used to reach `_settle_agent_fills`, which told a person and nobody else — the agent learned only whenever it next happened to wake, up to four days later. It now also calls `scheduler._maybe_run_agent("Stop fill")`. A position left with nothing resting under it — a fill with no usable level, a bracket the broker refused, a failed sell that could not get its exits back — used to be a DB alert and nothing else. `agent.AgentRun.unguarded` now records it, and `scheduler._run_agent_pass_locked` calls `wake_agent_now("Unguarded position")` right after the pass's own alarm is set — **never during the pass itself**, which is the mistake "Never ask the agent again from inside a pass" below already warns about: calling it mid-pass would just be overwritten by that same pass's own `_replace_wakeup_alarm` call when it finishes. The pass that caused an unguarded position is also told in the same breath, in `_execute_orders`'s own outcomes, since it is usually still mid-loop when it happens.

   **The rule carries two worked examples of a good note, and they must stay**, because a worked example beats a prohibition: they moved notes naming a concrete price level from 0 of 7 to 4 of 7 (`agent-probes.md`).

   **A pass that acts and is asked again is several turns of one call chain, and until 2026-09-17 a note written in an earlier turn was invisible to a later one.** `next_wakeup_note` above is the *previous pass's* note, stable for the whole loop because `_record_run` has not run yet — so a turn only ever saw what the pass before it left, never what it or an earlier turn of itself had just written. `run_once` now keeps `notes_this_pass`, every distinct note the pass has written so far, and `describe_wakeup` shows it as its own labelled block, beside, not instead of, the previous pass's note. Seen live: a note set in turn 1 was gone by turn 2. See the 2026-09-17 JOURNEY.md entry.

   **The same gap existed one boundary later, and was fixed the same day.** `AgentRun.wakeup_note` was overwritten every act-turn, so only whichever turn happened to run *last* ever reached the *next* pass — a note from an earlier turn, never restated in the pass's final answer, was silently dropped at the pass boundary too. `_encode_wakeup_notes` now stores every distinct note the whole pass wrote (plain text for one, same as always; a JSON list for several, the convention `turns` already used), and `_last_pass_notes` reads it back — a pre-2026-09-17 row has no brackets, so it still reads as the single note it always was. `describe_wakeup` shows it as "Notes you left yourself last pass", oldest first, when there is more than one; `_last_wakeup_note()` stays a thin wrapper returning just the freshest one, for the early-wake case above, which is tied to a specific planned time rather than the pass's whole history.
2. **The regime line** when one is available — VIX, SPY against its 200-day average, the yield curve, as one sentence.
3. ~~**Recent changes to the app.**~~ **Removed 2026-09-21, with the whole mechanism behind it.** The agent is no longer told when the app changes. See the JOURNEY.md entry for what that costs and what to watch; the note number is kept so the references elsewhere in this file still resolve.
3b. **Persistent long-term memory notes** (`side: memory`), injected when any exist. Stored in DB setting `agent_memory_notes` (capped at 10 notes, max 500 characters per note, FIFO eviction).

   **Read when the note bears on the decision in front of it, and skipped when something more urgent has claimed the pass** — 0 of 4 on a crowded live book, 3 of 4 on a book where the note named a ticker with a live, affordable signal. **Do not read a quiet run on a crowded book as evidence the feature does not work**; rebuild the scenario first. The samples, the quotations and the `action: clear` oddity are in `agent-probes.md`.
4. **The account**: total budget, uninvested cash, total equity with its return against the budget, realized profit — plus how much of the cash is unsettled, when any is. Unsettled money is spendable but a buy made with it cannot carry its stop and target in the same order, which is the real restriction on a cash account. The *broker's* balance is never shown. The simulated account holds $1,000,000 and the agent is given a small fraction of it; if that number reached the prompt the budget would be meaningless.
5. **Holdings**, a table since 2026-09-15 (was one prose line each; see JOURNEY.md): ticker, shares, average cost, current price, the low and high it has traded since purchase (from the bar cache, via `agent.price_range_since_purchase`, when one is available), market value, unrealized profit, share of the account, days held, and the stop and target actually resting at the broker. **A missing stop or target says `UNSET`**, plainly, in its own column — the agent cannot move an exit it cannot see, nor notice one that was never placed. **The price-range column is unconfirmed as read** — nine samples, three placements, no quotation (`agent-probes.md`). Kept anyway: correct, rendered, cheap, and may be read by a different model. Do not treat its presence as proof the agent uses it.
5b. **Orders still pending a fill**, shown only when one exists (2026-09-17): ticker, side, shares, limit price, when it was placed. A limit order is invisible in the Holdings table above until it fills — it is not a position yet — and the outcome line that first announced it belongs to the pass that placed it and is gone from every later one. Without this a GTC order could sit for days with nothing in the prompt saying it still exists, and a later pass could place a second one on the same ticker having lost track of the first.
6. **Recent analyst signals**, up to 12 from the last 3 days, filtered to the model the app is configured to use. A table carrying decision, current price, day's high and low session range, suggested entry, stop and target, chance of working, risk/reward, expected value, **what of it the agent already holds**, and affordable shares. **Since 2026-09-19 the legend says the entry, stop and target are computed by the app from the verified close and ATR**, so the stop clears one day's normal range, and that a price inside an analyst's text is the analyst's own. It called them "the analyst's proposed levels" until then, and on 2026-09-15 the agent took the text's $97.00 stop over the table's $89.71 and was stopped out in 100 minutes.

   **`You hold` was added 2026-09-21, from the model's own report.** Asked what it had to carry from one part of the prompt to another, 11 of 14 samples named this pair: a holding's shares, average cost and resting stop, held in mind from "What you hold" while reading that ticker's row here (`agent-probes.md`). The two sections are already adjacent, so no reorder could reach it — the row did not say the position existed. The cell reads `7 since 18 Sep, avg $205.44`, or `—`, and it sits beside `You could buy`, the other column about the agent rather than about the stock. **The resting stop is deliberately not repeated**: the `Stop` column beside it is the app's computed level, and two stops in one row is the confusion the `Price now` / `At analysis` legend exists to prevent.

   **`Why it ran` was removed the same day, and half of it was kept.** The column named what triggered the analysis, and **nothing but the agent has triggered one since 2026-09-12** — 20 of the 21 signals this database has ever held say `commissioned`, and the single `move` row is dated the day before that change, so no other value can appear again. It had become one sentence repeated on every row. `Signal.trigger` is still recorded and the research page still shows it; this was about what the prompt spends a column on. **The in-pass marker is not repetition and stays**: a row the agent paid for in this same pass reads `2026-09-21 09:05 — **YOU paid for this one, in this pass, minutes ago**`, appended to when it was analysed. That marker exists because the model was measured citing its own research as "the analyst" — see "Provenance belongs on the row" in `describe_signals`. `_TRIGGER_PHRASE` went with the column.
7. **Every tracked ticker**, held or watched-only, one line each in a table: current price, day's high and low session range, and either "Never analysed" or the date and price of the last analysis, percentage moved since, and decision. Since 2026-09-08 nothing is analysed on a schedule — this is the ambient signal telling the agent if a name has gone stale or was never looked at. `describe_watchlist` renders it, and the `watchlist` fetch returns the same table on the tool channel. **On the tool channel the prompt carries one line instead (since 2026-09-17)**, from `describe_watchlist_brief`: the count, the names never analysed, and the names that moved `_BRIEF_MOVE_PCT` (5%) or more since their last analysis, then "Call watchlist for every one". The line keeps the stale-name signal the table existed for; everything else in the table is one fetch away.

   **A row past `_BRIEF_MOVE_PCT` carries a STALE marker in its `It said` cell (2026-09-22), and a held row says more.** The marker names the move, says the decision was made about a different price, and asks for a fresh look; a held row adds that the stop and target resting under the position came from that analysis and no longer say where the thesis breaks. The legend now states the threshold and the conclusion instead of the old permissive "a fresh look may be worth paying for". **The threshold is read from `_BRIEF_MOVE_PCT`, never written out again** — `describe_watchlist_brief` above already owns that number, and a test pins the legend to it. **Probed before it was built, by post-processing the function's output in the probe process: staleness in the reasoning went 1 of 7 to 7 of 7.** Research orders went 1 of 7 to 4 of 7, a swing of 3, which is inside the noise floor and is not claimed. **The marker's instruction about exits does not work** — stop adjustments on the stale held name went 3 of 7 to 4 of 7, and one sample called the old stop "potentially irrelevant" and raised it to an invented number anyway. **Do not answer that with more prose**; it is a habit, and the only thing that would reach it is a refusal in `screen`, which is a restriction and needs its own JOURNEY.md entry first. See `agent-probes.md` for both arms.

   **The candidate menu follows it on the JSON channel only (since 2026-09-17).** Up to fifteen screened names the agent may research, from `describe_menu`. On the tool channel the prompt carries one line saying to call `candidates`, and the screen runs once per pass, on that call, cached in the pass's allowance dict; a research of a new ticker must name one of what it returned. See "How the answer comes back".
8. **Its own track record**: closed trades, how many were profitable, the net result, the average holding period, and the last six individually with what the analyst had said at entry. Once it has bought on a Hold signal twice, it is told how that worked out specifically — that being the pattern it actually falls into. On the tool channel (since 2026-09-17) it is the totals and the Hold line only, from `describe_history_brief`, and the `track_record` fetch returns the trades.
9. **How long an analysis takes**, from its own recent runs, and what is being analysed right now with how long it has been running. It cannot plan a wakeup around research it ordered without both.

   **Bounded to the last seven days as well as the last twenty runs (2026-09-21).** `analysis.recent_durations` had a row count and no date bound, so it reached back to the first analysis this database ever held and averaged `qwen-3.8-27b` at 2.3 to 4.4 minutes together with the current model at 3.2 to 9.1. The line said "about 4 minutes — recently between 2 and 9" when the last five runs had taken 4.5 to 9.1. **Erring low is the expensive direction**: the agent plans a wakeup around this figure. After a quiet week `describe_analysis_timing` says nothing about duration rather than quoting a model no longer in use, and the section carries only what is running now. `_DURATION_DAYS` is 7.
10. **Its recent wakeups**, and whether each led to an action. Feedback rather than a limit: waking costs nothing, so pricing it would be an invented cost, and whether the agent learns to space them is a result worth having. On the tool channel (since 2026-09-17) the six timestamps are one count line, `describe_recent_wakeups(brief=True)`, and the advice under it is the same.
11. **What it asked to read**, when the previous turn asked for an analysis, under the heading `## What you asked to read` (a bold line until 2026-09-21), its own section since 2026-09-16 — before that it ran on directly from "recent wakeups" with no divider between them. **Since 2026-09-15, also what was not carried out because it rode along beside a read in the same answer** — a buy, a sell, an adjust, an untrack, a note. A read changes the pass's control flow rather than the book, so only the read runs from an answer that asks for one; anything bundled beside it used to vanish with no trace. Caught live: the agent asked to read INTC and, in the same answer, to buy 50 shares and move its exits — the buy and the adjust were simply gone. The next prompt now names exactly what was dropped and says to resend it.
12. **What the rules noticed since the last pass** — the watchdog's own alerts, bounded by the previous pass rather than by a count, and which tracked tickers report earnings soon. Facts, with nothing done about them. **Its lead reads "Nothing was done about any of these, and nothing was analysed" since 2026-09-21**; it opened "These happened while you were away", which the heading already says and which the event-driven wake reason repeats word for word.
13. **What its own orders did, earlier in this same pass** — the fill and what is resting under it, the analysis it commissioned and what that analysis concluded, the untrack, the refusal. Same placement and the same reason. **Since 2026-09-20, moving a stop or a target names the level it replaced** — "moved stop from $330.00 to $334.16", not only the level it moved to — so this line can tell a stop being raised from one being loosened. See the 2026-09-20 JOURNEY.md entry.
14. **The rules** (below), then how to answer: the JSON shape on the JSON channel, or one line saying to call `decide` on the tool channel. See "How the answer comes back" below.

### The rules, verbatim

**The rules live in two places since 2026-09-10, split by whether they quote a number from the pass.** The fixed ones are in `SYSTEM_PROMPT`, sent once per call and never rebuilt. The ones carrying a figure — the cash limit, the watchlist cap, the trade horizon, the conviction floor, the research price — stay in the user message beside the numbers they name. `_FIXED_RULES` holds the first set; `build_prompt` assembles the second.

The system message opens:

> You are a disciplined portfolio manager. You answer with JSON only — no prose outside it. You never spend more cash than you have and never sell shares you do not hold.
>
> The rules below never change. The message that follows carries this pass's own figures — the clock, your cash, your holdings, the analyst signals — and the few rules that quote a number from them.

**On the tool channel, a Gemini deployment since 2026-09-17, the first paragraph reads instead:**

> You are a disciplined portfolio manager. You answer by calling the decide function — never with prose. You never spend more cash than you have and never sell shares you do not hold.

The second paragraph and every rule are the same text on both channels; `agent._system_prompt` builds both from one list, and a test pins the two identity paragraphs.

Then the thirteen fixed rules. The list below is all of them plus the dynamic ones, in the order the model reads them; a rule marked **(pass)** is the kind that carries a figure and therefore sits in the user message.

The opener above it, from `build_prompt`:

> You manage a small account of real money. Decide what to do with it now, if anything.

The rules block:

- The buys you place must cost `$X` or less in total, added up across every buy. Not each — in total. If placing multiple buys in one turn, allocate quantities so that `sum(quantity × price)` fits within your available cash.
- Orders execute in the order you list them, so a sell frees its cash for a buy listed after it. To buy something you cannot currently afford, sell something first and put that sell earlier in the list.
- You may only sell shares you hold. No shorting, no options. Whole shares only.
- What the analysts' decisions mean: Buy and Overweight mean they expect it to rise, Buy with the stronger conviction. Sell and Underweight mean they expect it to fall, so exit it if you hold it. Hold means the analyst would keep a position they already had; it is not a verdict on opening one either way. A Hold that carries an entry, a stop, a target and a chance is a plan the trader stage wrote and the manager did not endorse: read it, and judge it on those numbers rather than on the word. **Rewritten 2026-09-19.** It said "Hold means no action is recommended — if you do not own it, a Hold is not a reason to buy it", written for `gemma4:e2b` after it bought 98% of the budget on a Hold. The pipeline's own scale defines Hold as "maintain current position", and it said Hold or Underweight in 18 of 20 analyses over ten days, so the old wording left a cash book nothing to act on. See the 2026-09-19 entry in JOURNEY.md. **Probed the same day: 4 of 4 samples read the rule, paraphrased it, and acted on a Hold that carried a plan** (`agent-probes.md`).
- Some signals carry how good the analyst thought the bet was. [...] Signals without these numbers are not worse bets, only ones where the analyst did not say. **Moved into `SYSTEM_PROMPT` on 2026-09-16** — it names no figure from this pass.
- You can also move the stop and take-profit on something you already hold, without buying or selling any of it. Use side `adjust` with a `stop` or a `target` price, or both. The stop must be below the current price and the target above it, or the order would execute the moment it was placed. Raising a stop as a position gains is how a profit is protected; today's analysis is what tells you where the thesis now breaks. If a holding has an UNSET stop or is in unrealized profit, use adjust to set or raise its stop to protect gains.
- You can sell any position at any time, for your own reasons. You do not have to wait for a stop or a target to be reached, and you do not need an analyst to say Sell first. [...] A resting stop is a floor under a position, not a reason to leave it alone.
- **Size a position from its stop, not from a percentage.** Decide how much of the book you are willing to lose if the stop fires — one to two percent is a common frame for a swing trade — and buy the number of shares whose distance to the stop adds up to that. An analyst's sizing advice such as "3% to 4% of portfolio capital" is written for a fund that runs many positions at once; it is not advice for this book. The size is yours to decide, and your cash is the only limit. **Added 2026-09-19.** A frame, not a cap: Python still refuses only what cannot be executed as stated. Nothing said anything about size before, and the one trade of the first ten days copied the analyst's percentage: 4 shares, $392 of $10,000. **Probed 2026-09-19: 4 of 4 samples sized from the stop**, 17 to 20 shares where the live trade had been 4. **The wrinkle: sizing from a stop is only as good as the stop** — the sample that took the analyst's tighter text stop sized 95% of the book on a 1.5% paper risk. Watch for it before adding any rule about it (`agent-probes.md`).
- A buy or a sell defaults to a market order. Add `"order_type": "limit"` and a `"limit_price"` to name your own price instead — a buy fills at that price or better, a sell at that price or better. Add `"time_in_force": "gtc"` to let it wait past today; leave it out, or use `"day"`, and it is gone at the close if it never filled. **Added 2026-09-17.** **Unconfirmed unannounced (0 of 8, two models), read once announced by a change note (2 of 4)** — `agent-probes.md`. **That announcement channel no longer exists** (removed 2026-09-21), so this rule is now in the unannounced condition permanently.
- **A limit buy does NOT get a stop or target placed under it, even when the signal has one.** It is not filled yet, and may not fill this pass at all, so there is nothing to rest an exit on. The instant it fills you are woken and told the fill price — set the stop and/or target yourself then, with `adjust`, off the price you actually got. A limit sell needs no such follow-up: it can only close a position you already hold. **Added 2026-09-17.**
- **A GTC order keeps something tied up until it fills or you cancel it** — a buy keeps its cash reserved, a sell keeps its shares committed and unsellable again until it resolves. Neither is free to leave sitting. Use side `cancel` with the ticker to withdraw one that has not filled. This never touches a resting stop or target; move those with `adjust`, or sell the position. **Added 2026-09-17.**
- To have something looked at, use side `research` with a ticker and no quantity. It runs inside this pass: you are shown what it decided and the analyst's own reasoning, so you do not need to set a wakeup for it. [...] There is no daily count on how many you may commission, only cash. **Shortened 2026-09-21.** It opened "Nothing is analysed automatically, holdings included", word for word the opening of the "Paying for research" section above it, and then wrote out the wait-and-be-shown explanation that the timing line and that section each wrote out too. Three sections explained the whole of research; each explains its own part now. The phrase "runs inside this pass" deliberately stays in all three — one name for one thing, and the timing section is the only one that renders when there is nothing yet to research.

  **"Paying for research" gives the price a scale instead of warning about it (2026-09-22).** `describe_research_price` ended "A bad choice of what to study is a loss like any other, so spend it where you actually want a fresh look — not because it is free to ask." It now ends "That is cheap next to the cost of a trade you get wrong. Research anything you are unsure about." ### What Python enforces, regardless of what the model says

The division is deliberate and load-bearing: **the model decides what and how much; Python refuses what cannot be executed as stated, and never resizes.** Resizing would quietly turn its decision into a different one, and then the record would be of a strategy nobody chose.

- **Orders are screened against a running book, not the opening one.** Three buys that are each affordable alone are not necessarily affordable together.
- **An unaffordable order is dropped, not shrunk.**
- **The cash check includes the broker's 2% buying-power cushion, not only the 0.5% entry-limit buffer (2026-09-17).** `agent_book.buying_power_margin()` reads `sandbox_broker.BUYING_POWER_MARGIN_PCT`, the same constant the "You could buy" column already used. Before this, `validate` only screened at `entry_limit_price`, so an order could clear the Python check and still be refused at the broker — and since the rejection is what feeds the one retry, the model recomputed from the raw price, landed on the same unaffordable quantity, and resent it unchanged. Seen live: a refused 12-share AAPL buy, resent identically. The rejection text now names the cushion, so the retry has the real number.
- **A pending GTC limit buy reserves its cost against cash until it fills or is cancelled (2026-09-17)** — `agent_book.build_book` subtracts `quantity × limit_price` for every pending, unfilled limit buy. Before limit orders existed a pending order spent nothing, which was safe only because every buy filled within the same pass or by the next open; a GTC order can now sit for days, and without the reservation a later pass would see the same cash as free.
- **A pending GTC limit sell reserves its shares the same way (2026-09-17)** — `Book.reserved_shares`, checked in `agent_book.validate`. `holdings` is rebuilt from filled trades alone every pass, so an unfilled limit sell still shows the shares as held; without the reservation a later pass could sell them again before the first sell resolves. `screen()` keeps a running copy so cancelling the pending sell frees its shares for a sell listed later in the same answer, the same way an untrack frees a watchlist slot.
- **Sells cannot exceed holdings** — and since the margin account will short where a cash account refuses, that is now enforced in `sandbox_broker` too rather than inherited from the account type.
- **Exit levels that would execute on placement are refused**: a stop at or above the price, a target at or below it.
- **A held ticker cannot be untracked.** Since 2026-09-08 nothing is analysed automatically at all, holdings included — untracking a position would take away the only way left to ever research it again. Sell it first.
- **The watchlist is screened against a running copy too**, for the same reason as cash: an untrack listed before a research frees a slot for it, and two researches cannot share one freed slot. This only matters for a genuinely new ticker — re-researching one already tracked does not touch the count.
- **A ticker already tracked may be re-researched as often as the agent will pay for it, same day included.** Before 2026-09-08 this was refused outright, on the assumption that a daily sweep covered every tracked ticker for free. There is no such sweep now, so refusing a fresh look at something already tracked would mean it could never be re-analysed at all. A once-a-day guard (`has_signal_today`) briefly stood in its place and was removed the same day: an analysis finishes in about twenty minutes, and a price nearing its stop or target is exactly the case where a second look the same day is the right call. Cash is what bounds it now. `has_signal_today` still gates the watchdog's own automatic move-triggered re-analysis — a different question, the system deciding whether to auto-trigger rather than the agent deciding whether to ask. See the 2026-09-08 entries in JOURNEY.md.
- **A closed market refuses the order, never the pass.** Until 2026-09-10 `run_once` returned before the model was asked whenever the session was shut, which made the prompt's standing invitation to wake early and commission the open's research quietly untrue. The venue's refusal is about orders; research, moving a stop, untracking, leaving a note and choosing the next wakeup all work at any hour. `market_clock.describe()` is the first line of every prompt and says which it is, and an order sent anyway comes back as a broker failure that the next prompt shows. **Do not add a timing gate here again** — the two gates in `run_once` are the sandbox boundary and the on/off switch, and neither is about the clock.
- **Nothing but the agent commissions an analysis (2026-09-12).** A sharp move and a volume spike used to nominate a ticker for one, and the pre-market earnings check did the same. Both decided what the agent should study, and both were billed to the agent's research budget — **every analysis charges, whoever ordered it**, which is what made this a real cost and not just a philosophical one: ten charges on the live book that the agent never asked for. `watchdog.scan_for_alerts` returns alerts only, `AlertCandidate` has no `trigger_analysis`, `earnings_due` replaces `earnings_tickers_to_analyze`, `_run_triggered_analyses` is deleted rather than left dormant, and `db.has_signal_today` went with its last caller. **Do not add a path that analyses something the agent did not order.**
- **Triggered wakes are not gated on market hours.** The gate existed because a move worth *analysing* at midday is worth nothing by morning; nothing analyses now. The earnings check runs pre-market and under that gate could never have woken anyone.
- **"What you just did" and "What was noticed" sit above the signal table, and that placement was measured**, 0 of 4 runs below the tables against 4 of 4 above them (`agent-probes.md`). **Do not move them back down. Probe the prompt by reading the reasoning, never by assuming a section is read because it renders.**
- **Alerts are bounded by the previous pass, not by a count.** The first version took the newest eight whatever their age, so a Saturday pass was shown Thursday's moves under a heading saying "noticed". With no previous pass, 24 hours is the fallback.
- **A pass is a loop: act, see what happened, be asked again (2026-09-12).** `run_once` rebuilds the book, the prices and the signals on every turn, because a buy changed the cash and a research order put a new analysis in the table the next turn has to see. It ends when an answer does nothing — which is also what "no orders, wake me later" looks like — or at `_MAX_ACT_TURNS`, raised from 3 to **8 on 2026-09-15** once research dropped from 16-20 minutes to 9-10 (a research turn holds `_pass_lock` for the whole wait, so 3 of the old duration was already a possible hour-long pass). Unlike the read allowance below, this number is never shown to the model. The read allowance is **one dict shared across those turns**, so six reads a pass cannot become eighteen.
- **An answer repeating the previous turn's orders ends the pass.** Acting is not reading: executing a repeat would buy twice, and screening only catches the second buy once the cash has run out, which is far too late. The prompt also says what has already been done and not to place it again; the guard is what makes that safe rather than hopeful.
- **Research runs inside the pass, and the scheduler supplies the bridge.** `run_once` is synchronous on a worker thread; an analysis is async work owned by the main loop. `scheduler._research_for_agent` is installed on the agent by `register_jobs` and blocks on `run_coroutine_threadsafe`, which keeps `agent.py` synchronous and free of a scheduler import. **The cost is that `_pass_lock` is held for the whole analysis**, about sixteen minutes, and that is deliberate — see the 2026-09-12 entry in JOURNEY.md.
- **Never ask the agent again from inside a pass.** That was the old shape and it never once worked: the pass dispatched its research, then called `_maybe_run_agent` while still holding `_pass_lock`, whose first line is `if _pass_lock.locked(): return`. Seventeen analyses across two days produced no pass at all. The prompt had promised "you are asked again automatically", which made it a lie the agent planned around.
- **A failed analysis is retried, reported as failed, and never charged twice (2026-09-13).** Until then a failure inside the pass was told to the agent as "It has finished", beside the older analysis. `analysis.failure_kind` sorts a failure four ways: the model service not answering (a doubling wait from 30 seconds, capped at ten minutes a step and one hour in total, asking the endpoint whether it answers before running again), the service refusing access (401, 402, 403 — Cerebras' 402 when its credits ran out would not clear in an hour, so it is reported at once), the day's stated request limit (reported at once), and an error in this app (retried once). **Recording is retried on its own**, because the charge lands between the model work and the record, and running the analysis again would charge twice. **The retry loop awaits `_one_attempt`, not `propagate_ticker`**, so `test_analyses_are_dispatched_together` does not read one ticker's retries as the loop-over-tickers bug — do not inline it. **The hour is a bound on the pass, not a ration**: the pass holds `_pass_lock` for the whole wait.
- **A read earns its own follow-up turn, separate from a refusal's retry since 2026-09-10.** `read` never reaches `screen` — it moves no cash, no shares and no watchlist slot — so it is split out in `_decide` before screening, because it changes the control flow rather than the book. Up to `_MAX_READS_PER_PASS` (6) reads and `_MAX_READ_TURNS` (3) follow-up turns are allowed per pass, in one dict shared across every act-turn so the budget cannot be multiplied by asking again. This bullet used to say a read shared its one follow-up turn with a refusal's retry and that a second read was dropped outright — both true before 2026-09-10, neither true since; corrected 2026-09-15 rather than left for someone to trust literally.
- **A read asked for on a refusal's retry turn does not run, and the prompt says so up front (2026-09-15).** The retry is the pass's last turn — there is no further turn to spend showing the read's result. Before this date nothing told the agent that: `_decide` quietly dropped the read half of that answer (`_split_reads` again) and screened whatever else came with it, so a model that tried to read there paid its one chance to fix a refusal for nothing and never learned why. The "Your previous answer was refused. Fix it:" block now says plainly that a read does not run on that turn. Anything bundled beside the read in that same retry answer is unaffected either way — it was never dropped, only the read was.
- **A read resolves by ticker and an optional date, and sorts locally.** `db.get_recent_signals` orders by `signal_date` alone by default, which is a calendar date, so two analyses of one ticker on one day come back in row order — asking for INTC's 2026-09-08 analysis returned the 19:06 one over the 19:18 one. `analysis_reader` sorts by date, then `created_at`, then id, using `signals.newest_first` — one copy of that key, shared with the research page, which had the same fault for the same reason. **Do not change the query's default ordering: every other caller reads it.**
- **Since 2026-09-19, a read opens with a levels line** whenever the signal carries an entry, a stop or a target: which numbers the app computed from the verified close and ATR, and that a price in the text below is the analyst's own. `analysis_reader._levels_line` writes it, before the rationale, and writes nothing for a signal with no levels. Same incident as the table legend above: the 2026-09-15 INTC trade took the text's stop over the table's. **Probed the same day: 4 of 4 samples told the two stops apart, and 3 of 4 chose the app's** (`agent-probes.md`).
- **Since 2026-09-15, a read also carries evidence from the four analyst reports**, not only the Rating and the rationale — before this, `market_report`, `sentiment_report`, `news_report` and `fundamentals_report` were computed and stored for every analysis and never reached the agent. **Restructured 2026-09-16**: the first version trimmed each report to 500 characters of prose, which cut mid-sentence wherever the count landed. `analysis_reader._analyst_snapshot` now pulls each analyst's own summary table instead — every analyst prompt already ends with an instruction to append one — via `_last_table`, which takes whatever heading the model gave it rather than guessing a fixed title. `investment_plan` and `trader_investment_plan`, already stored per signal, are now included in full (each runs under 2,000 characters and is what the model's own final call drew on). A report with no table, or nothing on record at all (a signal from before this date, or a row that never saved), is left out rather than shown empty.

  **Probed twice, and the finding splits the section in two: the two full plans get read, the four report tables do not.** 2 of 4 samples cross-referenced `Investment plan` and `Trader's plan` and caught a real contradiction between them; 0 of 4 quoted anything unique to the Market, Sentiment, News or Fundamentals tables. **Keep the plans. - **Sorting after the fetch is not enough when a LIMIT is involved**, which is the one case that needs the query. Measured on the live book 2026-09-11: `limit=10` returned 2026-09-10's four oldest and dropped its seven newest. `get_recent_signals` therefore takes an opt-in `by_time=True` that adds `created_at` and `id` to the ORDER BY. Opt-in, not the default, for the reason above.
- **`Signal.created_at` is when the analysis *started*, for every row.** It meant the finish on rows written by `record_signal` and the start on rows recovered from `trace_id`, about sixteen minutes apart, until 2026-09-11. The start won because it is the instant actually observed — `trace_id` encodes it — where a finish has to be computed. `propagate_ticker` puts it in `final_state["started_at"]` and `record_signal` passes it down; `backend/scripts/backfill_signal_timestamps.py` resets every row that carries a trace_id and is safe to re-run. - **A refused order is fed back once** and the model asked again, which is how it learns it may sell to fund a buy, and untrack to fund a research. The advice in that retry is matched to the refusal — cash advice does not help a full watchlist, and the first live probe produced exactly that mistake.
- **The clock knows the NYSE calendar, and it is computed rather than listed.** `market_clock.describe()` had no holidays at all, so on Labor Day 2026-09-07 it read "the market closes in 5h 28m, at 4:00 PM" and the agent placed five orders across three passes that the venue refused — **five of the six market-closed refusals in the whole record are that one day**, and the sixth is a Saturday. `market_holidays()` derives all ten closures from the published rules (including Good Friday from Easter, and the Saturday-to-Friday / Sunday-to-Monday observance), `early_closes()` covers the three half-days, and `next_open()` skips both. **No dependency and no table**: a table is a copy of the rules that goes stale the year nobody updates it. ### How a position is opened and protected

A buy goes out as a **bracket**: a `MASTER` entry with `STOP_PROFIT` and `STOP_LOSS` legs, one submission, one shared combo id. The broker activates the exits when the entry fills, so the shares are never held with nothing under them. The entry is a marketable limit rather than a market order because Webull refuses a `MARKET` master — and the limit caps slippage, which matters on an app-enforced budget.

When the stated stop is unusable, one is derived from 2×ATR(14) at the moment of purchase. When a combo is refused — which happens routinely, because a cash account will not accept one against unsettled funds — it falls back to a market order plus separately-armed exits.

**Arming a fresh exit always cancels whatever is already resting on the ticker first (2026-09-17).** `_arm_exits` and `adjust_exits`'s arm-new branch used to place a brand-new stop and target without checking the broker's own state, trusting the local ledger's "nothing resting" as if it were ground truth. AVGO was topped up, its bracket was refused a second time for unsettled cash, and the fallback armed a second stop and target on top of the first still resting from the earlier buy — the broker then saw more shares committed to sell than the account owned and refused three identical `adjust` retries with `OPENAPI_ORDER_NOT_SUPPORT_REVERSE_OPTION`, clearing only when an unrelated sell elsewhere in the pass happened to cancel the stale order. Both call sites now run `_cancel_resting_exits` + `_await_cancels` first — the same guarantee `_sell_and_restore_on_failure` already gave a plain sell, extended to arming. A no-op, and no extra latency, on a genuinely new position.

**Since 2026-09-17 a buy or sell may also be a limit order** (`"order_type": "limit"`, a `"limit_price"`, and `"time_in_force"` of `"day"` or `"gtc"`), placed with `sandbox_broker.place_limit_order`. A limit buy is never bracketed — the broker will not hold a combo's exit legs inactive against a master that might not fill for days — so it goes out alone and its stop/target, if the signal had any, are left unplaced. The agent is woken the instant the fill is confirmed (`scheduler._settle_agent_fills`, mirroring the existing stop-fill wake; see `agent.format_limit_fill`) and sets the exits itself then, with `adjust`, off the real fill price rather than a price guessed at order time. A limit sell still clears resting exits first, exactly like a market sell — the broker refuses any new sell while something rests on the position, regardless of order type.

**The mechanism is unconfirmed as chosen, on both models tried**: 0 of 8 reached for a limit order on a textbook case for one, and told its own plan by name, each model produced the correct order on only 1 of 4. **The local model's misses are the concerning ones** — the words "executing the disciplined limit buy" over an order carrying no `order_type` at all. Kept, because a market order is still the safe default outcome, but do not treat the feature's presence as proof the agent will reach for it, and re-probe after any placement change. Both runs are in `agent-probes.md`; see the 2026-09-17 JOURNEY.md entries.

**A GTC order's cost stays reserved against cash until it fills or is cancelled** (`agent_book.build_book`, `agent_book.validate`). Before this, a pending order spent nothing — true only because every buy used to fill within the same pass or by the next open; a GTC limit buy can now sit for days, so leaving it unreserved would let a later pass commit the same dollars twice. `{"side": "cancel", "ticker": "..."}` withdraws a still-unfilled entry order; it never touches a resting protective stop/target, which stay reachable only through `adjust` or a sell.

### How the answer comes back (2026-09-17)

**Two channels, chosen by provider.** `agent.answers_by_tool()` is true on the google provider, and `AGENT_ANSWER_CHANNEL=json` turns it off without a rebuild. Everywhere else the model writes JSON into its reply and `parse_decision` reads it, with its two repairs and its salvage step, all of which exist because a local model fenced, wrapped and mistyped its JSON.

**On the tool channel the model must call one function, `decide`, and cannot answer with prose.** `backend/services/llm_gemini.py` makes the call through Google's own SDK, not the LangChain wrapper the analysis graph uses: TradingAgents' Google client flattens every reply to a string, which drops a function call, the thought parts and the thought signatures a later multi-turn call has to send back. The module builds one `genai.Client` from `GOOGLE_API_KEY` and attaches the throttle to it, so a decision pass counts against the same per-minute and per-day limits as an analysis. The call sets `mode ANY` with `decide` as the only allowed name, `system_instruction` to `SYSTEM_PROMPT_TOOL`, and a thinking config at `TRADINGAGENTS_GOOGLE_THINKING_LEVEL` when one is set. The arguments come back as the same JSON text every answer has always been, so `parse_decision`, `parse_wakeup`, `parse_wakeup_note`, `_turn`, the record and the Decisions page are untouched. Whole-number floats become ints on the way (`llm_gemini.plain`), because the API types every number as a float and a `2.0` in the record would read differently from every earlier `2`.

**The schema is `backend/services/decision_schema.py`, and every side is its own object.** A flat object with every field optional cannot say that a buy needs a quantity and a note does not. `order_type` is required on a buy and a sell, so a market order is a choice the model makes rather than a default it falls into; that is the 2026-09-17 finding, where the model wrote "limit" in its reason and sent an order with no `order_type`. The schema uses only `type`, `enum`, `description`, `properties`, `required`, `items` and `anyOf`, and a test refuses any other keyword, because a keyword the vendor does not support fails the whole call. **The schema constrains shape, never truth**: `screen` still refuses everything it refused before.

**The prompt changes by two sentences and one block.** The identity paragraph of the system message says to call `decide` rather than to answer in JSON; the last fixed rule ends with the same instruction; and the "Answer in this shape" example at the end of the user message is replaced by one line, because an example the model is told to copy would sit beside a function it is told to call. `build_prompt(answer_by_tool=True)` does the cut, and `_decide` reads the channel once per pass so every turn is built the same way.

**Fetches run inside the same call (2026-09-17).** Beside `decide`, `decision_schema.FETCHES` declares `read`, `candidates`, `fundamentals`, `watchlist` and `track_record`. `llm_gemini.decide` offers them while the pass's allowance lasts, runs each through `ToolContext.fetch`, appends the result as a function response under the `user` role (the API refused `tool` on the first live pass, whatever the SDK's README shows), and asks again; several fetches in one round cost one round, a fetch past the allowance is answered with `ALLOWANCE_SPENT` rather than run, and a `decide` in the same round as a fetch is answered with `DECIDE_WITH_FETCH` and not carried out, the rule the read side has always had. `_fresh_budget` is the pass's allowance dict, owned by `run_once`: `fetches` and `rounds` bound the tool channel (`_MAX_FETCHES_PER_PASS` 30, `_MAX_FETCH_ROUNDS` 6 since 2026-09-19; 12 and 5 before, its own numbers since the first live probe hit the old six after three reads), `reads` and `turns` the JSON channel's read loop (6 and 3), `menu` caches the candidate screen for the pass, and `fundamentals` (since 2026-09-19) caches each ticker's figures the same way, so a second call for one ticker does not reach Yahoo again. **`fundamentals` is unconfirmed as read** — 1 of 4 samples called it and 0 of 4 quoted a figure from what came back (`agent-probes.md`). Same status as the four analyst-report tables: the tool works, and its presence is not proof of use. **A fetch never reaches Google; a round is one Google request that resends the whole conversation**, which is why the rounds stay few and the fetches need not. When a round leaves one more, or none, the last function response of that round carries `ONE_ROUND_LEFT` or `NO_ROUNDS_LEFT` under a `rounds` key of its own, so the result stays verbatim and no part the API did not ask for is added; the record gets a `rounds` row in `exchanges` at the same point. **`ToolContext.fetch` never raises**: a failure returns as the result text, and names nothing to try instead. On this channel `read` is not a side (`decision_schema.order_schema(with_read=False)`), the prompt names `candidates` instead of listing the menu, and `screen`'s universe for a new ticker is what `candidates` returned this pass, an empty set until it is called. A fetch with no arguments declares no `parameters_json_schema` at all, because the API refuses an object schema with no properties. Each turn's `exchanges` (name, args, result, in order) are stored on the turn, a single-turn pass that fetched keeps its turn (`_turns_worth_keeping`), and the Decisions page shows them.

**A failed call falls back to the text channel, loudly.** `_invoke_by_tool` catches everything but the day's request limit, logs a warning with the traceback, and asks through `_invoke` with the JSON system message and `_FALLBACK_SHAPE` appended to the user message, because the tool-channel prompt shows no JSON example for a text answer to copy (the first live fallback came back without a `reasoning` key). **Every turn records its `channel`** (`json`, `tool` or `text-fallback`, on `_Answer` and in `_turn`); `_turns_worth_keeping` keeps a single fallback turn, `fallback_turns` counts them for the Discord embed's warning field, and the Decisions page flags the pass. A fallback turn was otherwise identical in the record to a tool turn that fetched nothing.

**Confirmed live on 2026-09-17, in a local container on the same image** — 4 of 4 samples fetched and answered through `decide` (`agent-probes.md`). A pass costs 3 to 4 requests and 20,000 to 30,000 prompt tokens, since each round resends the conversation, and `prompt_tokens` on the record sums the rounds. `backend/scripts/probe_prompt.py` makes the same call on a google deployment, fetch loop included, so a probe tests the channel production uses; it has to run inside a container, because the host cannot reach Google.

### Probe the prompt: send it to the model and read the reasoning

**A prompt change is a hypothesis until the model's own reasoning confirms it.** `python -m backend.scripts.probe_prompt --turn turn1 [--parallel]` builds the real prompt from a copy of the database and calls the model out of the app — it never reaches `run_once`, `screen` or any broker path.

**Run the `probe-the-prompt` skill and follow it.** It holds how to read a result, what decides where a section goes, and the four traps: the four prompt bugs that rendered correctly and were read past, "tables get read and prose gets skimmed", "do not grep the reasoning for the words you wrote", and the double-sent system prompt. Do not copy any of that here — one stale copy of it is worse than none.

### Before changing the prompt

Add the entry to **[JOURNEY.md](../../JOURNEY.md)** first, with the date and the reason. A month of runs across an undocumented prompt revision cannot be analysed, and the temptation to reconstruct the reasoning afterwards produces a story about what we would like to have been thinking.

**Then re-check "The rules, verbatim" above in the same edit.** That section quotes the prompt, and a quotation is stale the moment the original moves. By 2026-09-10 it had drifted three ways at once: it quoted a system message that still said "paper-trading" when the code had dropped the word a day earlier, it was missing the sell-any-time rule entirely, and it was missing the rule about a sharply-moving stock being analysed unasked. **A wrong quotation here is worse than no quotation**, because this file is what gets read instead of the code.
